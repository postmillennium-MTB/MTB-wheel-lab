# Wheel Strength Lab — source

This is the buildable source behind `postmillennium-mtb/MTB-wheel-lab`'s
`index.html`. The deployed site is still a single self-contained HTML file —
that hasn't changed — but it's now *generated* from real, readable source
files instead of being the only copy of the app that exists anywhere.

## Why this exists

The original `index.html` was a 600KB single-line minified bundle with no
separate source, frozen dependency versions, and no error handling if a
calculation crashed. This directory fixes that:

- **`src/`** — readable, organized source (see below)
- **`build.js`** — rebuilds `dist/index.html` from `src/` using esbuild
- **`test/`** — automated regression tests (physics math + a full-app smoke test)
- **`.github/workflows/test.yml`** — runs the tests on every push. This one
  lives loose in the repository rather than inside `wheel-lab-source.zip`,
  because GitHub only reads workflow files at that path in the repo itself and
  never looks inside an archive. See **Continuous integration** below.

## Continuous integration

Every push and pull request runs `.github/workflows/test.yml`, which unpacks
`wheel-lab-source.zip`, installs dependencies, rebuilds the bundle, runs both
test suites, and then checks that the committed `index.html` is byte-for-byte
identical to that fresh build. Green means the source is sound *and* the
deployed file is the one that source produces.

That last check is the point. Because `index.html` is uploaded by hand rather
than generated by the workflow, the failure this repo is actually exposed to is
the two drifting apart — the archive updated without re-uploading the built
file, or the deployed file edited without updating the archive. A build passing
proves the source works; only the comparison proves the source is what is live.
If it fails, download the `index.html` artifact attached to that run and commit
it.

The workflow needs the unpack step because the buildable source ships as a zip
rather than as loose files; `npm` cannot see `package.json`, `build.js` or
`src/` until it is extracted. The dependency audit runs but does not fail the
build: a new advisory published against a dependency would otherwise turn runs
red with nothing in the repo having changed, which only teaches people to
ignore red. Audit findings still appear in the run log.

## Where the physics comes from

The wheel-strength math itself doesn't live in this repo. It lives in a
separate, shared repo —
**[wheel-physics-core](https://github.com/postmillennium-MTB/wheel-physics-core)**
— because this tool and its sibling, `wheel-comparison-widget2`, used to
each carry their own hand-copied version of the same math, and those two
copies had quietly drifted apart. wheel-physics-core exists so that can't
happen again:

- It holds Matthew Ford's original reference math, **written in Python**
  (his `bike-wheel-calc` library, copied over unmodified — see that repo's
  README for the full attribution).
- It also publishes a **JS** (JavaScript — the programming language that
  runs inside a web page, in the visitor's own browser, with no server
  involved) port of that same math, hand-written to match the Python.
- Every time that JS changes, an automated check called **CI**
  (Continuous Integration — a script that runs by itself the moment code
  is pushed, rather than only when a person remembers to run it) recomputes
  the same numbers both ways — once in the real Python, once in the JS —
  and fails loudly if they don't agree. That check is what "validated"
  means here: not eyeballed once, but re-proven on every single change.

This repo (and `wheel-comparison-widget2`) are each **plain HTML** — no
server, nothing running behind the scenes. What they actually ship is the
JS half: `physics.js` imports the already-checked JS engine straight from
wheel-physics-core at build time (see `package.json`), so the Python never
runs live and never needs to — by the time its JS port reaches a visitor's
browser, wheel-physics-core's CI has already confirmed it matches the
Python, line for line. `wheel-comparison-widget2` has no build step, so it
keeps its own synced copy of that same engine file instead — the two tools
end up running byte-identical math either way.

Lateral strength (`F_lat`, the sideways load at which the first spoke goes
slack) and buckling tension come from Ford's fully-discrete-spoke Mode
Matrix, where each spoke sits at its own position around the rim and
lateral and radial deflection are coupled. Stiffness (`K_lat`, `K_rad`)
uses his smeared-spoke formulas. Until October 2026 strength also used a
smeared shortcut; wheel-physics-core's `validation/strength/README.md`
records why it was replaced. A build at or past its buckling tension has no
meaningful strength figure, and the COMPARE tab says so instead of showing
one. With the measured rim below, no hub in the catalogue gets there inside
the tension slider's range (the closest, a 32" wheel with 36 spokes at
125 kgf, sits at 50% of its buckling tension), but the guard stays.

### The rim

Every build in the Lab uses one rim, held constant so that the comparisons
isolate the hub: the **DT Swiss TK540, as measured by Matthew Ford** with the
acoustic method in Ford, Peng and Balogun (2018), "Acoustic modal testing
of bicycle rims" (archived in wheel-physics-core as
`papers/ford-peng-balogun-2018-acoustic-modal-testing.pdf`). The values come
from Ford's [rim stiffness library](https://bicyclewheel.info/rim-stiffness/):

| Property | Value |
|---|---|
| Lateral bending stiffness, EI_lat | 260 N·m² |
| Radial bending stiffness, EI_rad | 211 N·m² |
| Torsional stiffness, GJ | 75 N·m² |
| Mass | 550 g |
| Axial stiffness, EA | 7.2 MN (not in the library; from the mass, as Ford's own wheel-app does: E·m / (2πrρ), alloy, 622 mm bead seat) |

Ford measured ten other rims the same way, all listed in the same library:
Alex ALX-295, X404 and Y2000 (26" and 700C), DT Swiss R460, H Plus Son
TB14, Mavic A119, Stan's Grail MK3, and Sun-Ringle CR18 (20" and 700C).
Seven of them are also the rim presets in Ford's wheel-app. His paper
reports the method agreeing with direct mechanical tests to within 8%
(radial) and 11% (lateral and torsional). None of the eleven is a wide
modern MTB rim; the TK540 is used because it is a current DT Swiss rim in
the middle of the measured range. The Lab does not offer a rim choice for
now.

Until November 2026 the Lab used EI_lat 50, EI_rad 150, GJ 22 N·m² and EA
11.5 MN, an unsourced placeholder softer laterally than any rim Ford
measured (the softest, a 26" Alex Y2000, is 130 N·m²). On the default build
(29" at the then-current ERD of 600 mm, 28 spokes, 120 kgf, CK Centerlock
pair) the measured rim roughly doubled lateral strength (F_lat 20.7 → 38.7
kgf for 148, 26.4 → 46.3 for 157) and lateral stiffness (K_lat 59.4 → 107.5
and 77.0 → 133.5 N/mm), and moved the wheel from 61–67% of its buckling
tension to 28–33%. Radial strength (F_rad) fell slightly, 212 → 197 and
220 → 210 kgf. With the sourced ERD of 605 mm for 29" (below) the default
build of that time (28 spokes) reads F_lat 38.3 and 45.8 kgf, K_lat 104.6
and 130.0 N/mm, F_rad 196 and 209 kgf, at 29–33% of buckling tension.

Since November 12, 2026 the default build is the one the 148 vs 157 widget
opens on, so a reader moving between the two tools sees the same wheel: the
CK Centerlock pair, 29", 32 spokes, 120 kgf drive-side tension. It reads
F_lat 42.5 and 50.9 kgf, K_lat 119.9 and 149.3 N/mm, F_rad 211 and 226 kgf. The SIMULATION tab's
illustrative ride loads were rescaled with the rim change (see
`RIDE_LOAD_SCALE` in `src/data.js`) so they keep the same relation to the
default build's lateral strength.

### Effective rim diameter by wheel size

The wheel-size selector sets the effective rim diameter (ERD, the diameter
the spoke nipples seat at), one value per size, each from a manufacturer's
published spec (`RIM_ERD_BY_SIZE` in `src/data.js`):

| Wheel size | ERD (mm) | Source |
|---|---|---|
| 26" | 538 | DT Swiss FR 560 26" ([spec page](https://www.dtswiss.com/en/components/rims-mtb/free-ride/fr-560), "Reference diameter ERD 538 mm") |
| 27.5" | 567 | Tenet Coven AL rim ([product page](https://www.ridetenet.com/products/coven-al-rim), "ERD 567 mm (27.5) / 605 mm (29)") |
| 29" | 605 | Tenet Coven AL rim, same page. Reserve 30\|XC lists 599 mm for 29" ([product page](https://reservewheels.com/products/30-xc)) |
| 32" | 649 | Reserve 30\|XC 32" ([product page](https://reservewheels.com/products/30-xc), "32\" ERD 649mm") |

These are single typical values, not the TK540's own ERD, and real rims
differ by a few millimetres (the two 29" figures above are 6 mm apart, which
moves F_lat about 1.3% and lateral stiffness about 3%). Until November 2026
the table read 534 / 559 / 600 / 667 mm with no source recorded.

Across the 30 hubs in the catalogue (`src/data.js`) at standard build conditions (29 in, 32H, 2.0 mm spokes, 100 kgf DS tension, the measured TK540 rim), K_lat ranges from **97.5 to 133.8 N/mm for 148** builds and **112.5 to 163.4 N/mm for 157** builds. The variation within each standard is as large as the difference between standards — meaning hub geometry and wheel size matter as much as the axle width.

### Does the ratio change with wheel size (27.5" vs 29")?

Yes, but only very slightly — wheel size is a minor, second-order effect on this particular metric. Running the actual engine across all four wheel sizes on a few different hubs:

| Hub | 26" | 27.5" | 29" | 32" | spread |
|---|---|---|---|---|---|
| CK Centerlock 157x12 | 71.85% | 71.81% | 71.77% | 71.73% | 0.12 pp |
| Project 321 G3 157x12 | 83.24% | 83.21% | 83.18% | 83.15% | 0.09 pp |
| DMR Zone Centerlock 148x12 | 55.64% | 55.60% | 55.56% | 55.52% | 0.12 pp |

(32H, 2.0 mm spokes, 100 kgf DS, re-run 2026-11-11 with the sourced ERDs
on wheel-physics-core `1a8109f`. Project 321 G3 157x12 reads higher than the 81.6% this table
showed before the October 2026 correction to that hub's offsets.)

So going from 27.5" to 29" moves the ratio by roughly 0.04 percentage points — essentially nothing next to the tens-of-points spread you see just from switching hubs. The mechanism is real (larger wheel radius → both spoke bracing angles shrink slightly, and they don't shrink at exactly the same rate when the two flanges differ in offset or PCD, so the ratio drifts a hair), but it's swamped by hub geometry.

Worth noting: wheel size matters much more for the other three metrics — K_lat, F_lat, buckling tension — because those depend on absolute spoke length and rim stiffness, not just the angle ratio. The line above about "hub geometry and wheel size matter as much as axle width" is about K_lat, a stiffness, not tension balance.

The failure map, and the SIMULATION and DEEP DIVE tabs (once each, at the
foot of the tab), carry a short ISO 4210-7 note (`IsoNote.jsx`): the
standard's static test checks a rim for permanent bending under a sideways
load, while F_lat is the earlier, elastic first-slack limit, so the two are
different thresholds.

### The SYMMETRY tab's tension

The tension slider sets drive-side tension. On a real dished wheel the
non-drive side then sits well below it, so a centered wheel given the slider
value on both sides would carry about 20% more total tension than any real
wheel at that setting. On the Lab's earlier placeholder rim (see "The rim")
that put the tab's centered wheel at 81% of the rim's buckling tension and
past its own lateral-strength peak (24.3 kgf at 120 kgf against 26.3 at
100); on the measured TK540 it would sit at 40%. Either way, dishing it
would change total tension as well as balance. The tab therefore holds the average tension
constant at 5/6 of the slider value (`symmetryBuild` in `physics.js`): 5/6 is
the average of a wheel whose non-drive side is at two thirds of its drive
side, which is about where the catalogue's hubs sit on a 29" wheel (148x12
median 64%, 157x12 median 69%). The drive side's tension for a given offset
follows from the engine's own NDS/DS ratio. With the average fixed, the
distance from buckling is the same at every offset and lateral strength falls
at every step of dish, at every setting the controls can reach short of
buckling (asserted in `test/physics.test.js`).

### The tension slider's ticks

Under the Spoke tension slider, a tick and a caption give the drive-side
tension at which each selected hub's lateral strength peaks
(`peakLateralTension` in `physics.js`, a search on the engine's own F_lat).
Past that tension the wheel is close enough to buckling that more tension
lowers lateral strength. Ford's thesis (ch. 5) gives a rule of thumb for this
optimum, T_opt = 0.5 T_c, from an approximation he describes as rough and
conservative; the engine's peak for the default builds is nearer 0.65 T_c in
average-tension terms. On the measured TK540 rim those peaks (233 kgf for the
default 148 hub, 269 kgf for the 157) lie beyond the slider's 125 kgf, so
the ticks sit off the track and the caption still names both values: across
the slider's whole range, more tension means more lateral strength. The
ticks show on the tabs that use the two selected hubs.

### Start here tour

`Tour.jsx` holds a five-stop guided path for a first visit: the verdict
(COMPARE), why balance drives it (SYMMETRY), what gives first (the failure
map), mixed loads (the load envelope) and what margin looks like on a ride
(SIMULATION). Each stop opens its tab, scrolls to its chart, opens the chart
if the reader had minimized it (without changing their saved show/hide
choice), names it and says what to look at; the reader moves with Back and Next. The invitation sits at the top
of COMPARE until started or dismissed (remembered in the browser), and a
link in the footer starts the tour at any time.

### What-if bar

`WhatIfBar.jsx` pins a slim copy of the build controls to the top of the
screen once the main control panel has scrolled out of view, so a reader
deep in a chart can change the build and watch that chart answer without
scrolling back up (on a phone the spoke ring sits about 3,000 px below the
tension slider). On a phone it is one summary row that opens with Adjust;
on wider screens the hubs, spokes and tension sit in the bar, with the rim
one tap away. It drives the same state as the main panel. On SYMMETRY,
TENSION BALANCE and HUB SPECS, which don't use the two chosen hubs, it shows
only spokes, rim and tension.

After any change to the build, a "That change" strip lists how each hub's
lateral strength (kgf, load at first spoke slack) and lateral stiffness
(N/mm) moved, as two separately labelled chips, for about 3.5 s. A drag
through several slider steps is measured from where the drag started. The
chips sit in the pinned bar, or just under the main panel while that is on
screen. They are drawn in the text color with a sign and the hub named in
words, so they add no color pairs. Lowering tension shows the two moving in
opposite directions (stiffer, but weaker), which is the point of keeping
them apart. Motion is off under prefers-reduced-motion. The numbers are the
same engine outputs the rest of the tab shows.

### Compare these two, rider presets

TENSION BALANCE and HUB SPECS turn a pick into COMPARE's two hubs
(`CompareThese.jsx`). On TENSION BALANCE the highlighted rows are the picks;
on HUB SPECS a tap picks a row (ticked and barred, not color alone). COMPARE
holds one 148 and one 157 hub, so the newest pick of each standard is used;
a standard with no pick keeps the hub COMPARE already has, and the button
says "(already in COMPARE)".

The yardstick card on COMPARE has rider presets (Youth racer 45 kg, Trail
82, DH 100, E-bike 110: rough rider + bike weights, not survey data). They
set the Rider+bike slider, whose range now starts at 40 kg so the youth
preset fits. No strength or stiffness figure depends on rider weight; the
slider moves the yardstick, the SIMULATION ride and the TORSION rider load.

### Push the wheel, spokes at the dot

PUSH THE WHEEL (COMPARE, `PushWheel.jsx`) puts both builds side by side
under the same sideways push at the tire, toward the non-drive side, at the
spoke point that slackens a spoke soonest (the spoke ring's "Side → NDS").
Hold the button (or drag the slider) and the push grows; each spoke fades
as it loses tension and turns dashed at zero. The first wheel to lose a
spoke is marked at that load, which is its lateral strength `F_lat`, and
freezes there, because Ford's linear model ends at first slack; the other
keeps going until it too loses one. Under each wheel, "rim moved" is the
push divided by `K_lat`: stiffness, shown as a number, so strength (the ✕)
and stiffness (the mm) sit next to each other as two different things.
Nothing in the drawing is deflected or exaggerated.

The LOAD ENVELOPE (DEEP DIVE) draws the same face-on ring for the chosen
hub at the dot: every spoke under that down + sideways load, from the same
superposed responses the envelope's edge is built from. Outside the shape
the ring stops at first slack, scaled back along the same direction.

Both use wheel-physics-core's `spokeTensions` and `firstSlackCombined`,
already checked spoke by spoke against bike-wheel-calc, including combined
down + sideways loads (`validation/spokes/`, "combined"); no new engine
output.

### Hits on the load envelope (SIMULATION)

SIMULATION's first panel used to roll a random "chaos" ride, a scripted load
trace against the two lateral-strength lines. It now plots the four named
hits (rock strike, huck to flat, rock garden, cased a double) as numbered
dots on the chosen hub's load envelope (`HitMap.jsx`, reusing DEEP DIVE's
envelope chart). Each hit has a sideways part (`refPeak`) and a straight-down
part (`refDown`) in `IMPACT_SCENARIOS`, scaled with rider + bike weight the
same way as the slow-mo hit. Inside or outside the shape is exact in Ford's
model; the hit sizes are estimates, not measured trail loads, and the panel
says so. Inside is a filled circle, outside an open diamond, so the outcome
does not rest on color. All hits push toward the non-drive side, where the
envelope is narrower. The slow-mo panel plays only a hit's sideways part and
says so, which is why a hit can hold there and still slacken a spoke on the
envelope. The old ride's state and helpers (`simulateRideLoad`, etc.) are
left in place, unused, for now.

### Colors

A hub has one color in a theme, used for everything that belongs to that hub,
including its first-slack threshold on the SIMULATION chart; the ride-load
trace there is drawn in the text color, and the 148 threshold is dashed.
Roly-Poly's 148 color is a dark raspberry (#A21C5C): the lighter pink it
replaced had the same lightness as the 157 teal and merged with it under
deuteranopia. Known and not yet fixed: Roly-Poly's teal is 3.3:1 against the
panel background, short of the 4.5:1 that CLAUDE.md asks of small text; No
Quarter's 148 gold and its slack line are close under deuteranopia, and
Paperboy's 157 orange and its slack line under tritanopia (in the failure map
the hub color is only the title, the lines are labelled).

## A note on code style in physics.js and App.jsx

`physics.js`'s remaining local math (`bracingAngleDeg`, `applyRimOffset`,
`tightSideFirst`, and the ride-simulation/fatigue helpers) and the bulk of
`App.jsx` are left in a dense, short-variable-name style on purpose, rather
than fully rewritten with descriptive names throughout. (The actual
strength/stiffness calculation, `computeWheelStrength`, isn't local code to
style at all anymore — it's imported from wheel-physics-core; see "Where
the physics comes from" above.) Two reasons:

1. **Risk.** Hand-renaming variables inside a 20-term trigonometric
   expression is exactly the kind of edit that can silently introduce a
   sign error nobody catches in review. Every rename that *was* made
   (function names, module-level data references, component names) was
   verified mechanically — reversing the rename and diffing against the
   original bundle byte-for-byte — rather than trusted by eye.
2. **What actually helps.** The value of "readable source" here is mostly
   about being able to *find* things (a named `physics.js` instead of one
   line of 600KB) and understand what a function *does* (via the comment
   above it), not about every local loop variable having a long name.

If you want to make the internals more readable too, that's a reasonable
follow-up — just do it function-by-function with the same verify-by-diff
discipline, not as one big pass.

## Failure map

The COMPARE tab ends with a FAILURE MAP (`src/components/FailureMap.jsx`):
load against drive-side spoke tension for the two selected hubs, straight
down or sideways. The solid line is the engine's first-slack load (`F_rad` /
`F_lat`, Ford's discrete-spoke Mode Matrix). The dashed line is `F_taco`,
Ford & Balogun (2017) Eq. 2, a rough rim-buckling estimate that applies to
straight-down loads only; it comes from `wheel-physics-core` along with
`K_lat0` and `R_rim`. The sweeps (40 kgf to each hub's buckling tension, 3 kgf
steps, about 100 engine calls) run after the tab paints, and use the selected
rim size, spoke count and rim offset. The stat under the chart is the area of
one hub's shaded zone against the other's, from 40 kgf to each hub's buckling
tension.

The map shares its HUB toggle and Play crossfade with the spoke ring below
it (`FailureViews.jsx` holds the state, `HubFade.jsx` the hook and
controls), so either section's controls move both.

## Spoke ring and load envelope

Both draw from `wheel-physics-core`'s per-spoke output
(`calc(..., { spokes: true })`, `spokeTensions`, `firstSlackCombined`): each
spoke's tension change per unit point load from Ford's discrete-spoke Mode

## My wheel

The COMPARE tab's "My wheel" bar lets a reader save one build (a hub from
the list, wheel size, tension and spoke count) in their own browser
(`localStorage`, key `pmr-my-wheel`). It opens again on their next visit,
and the 148 vs 157 widget reads the same record through the PMR page that
frames it, so a wheel saved in either tool shows in both. A link that
carries a build always opens as sent; the bar then offers "Show my wheel".
"Forget" removes it. The record format is
`wheel-physics-core/js/my-wheel.js`. Only listed hubs can be saved, and
nothing is sent to any server.
Matrix, checked against his bike-wheel-calc in that repo's
`validation/spokes/`. `spokeModel()` in `physics.js` runs it for one build and
maps the engine's tighter/looser sides back to the real drive side when
`tightSideFirst()` has swapped them.

- **SPOKE RING** (COMPARE, `SpokeRing.jsx`): every spoke's tension under one
  hit at the tire, straight down or sideways either way, with a strip chart
  of the same tensions by distance from the hit. One load in kgf applies to
  both hubs, so Play shows one going slack before the other. Exact in Ford's
  model up to first slack; the slider runs to 130% of it, and past first
  slack the readout says the picture is an extrapolation.
- **LOAD ENVELOPE** (DEEP DIVE, `LoadEnvelope.jsx`, its own hub picker): every
  combination of straight-down and sideways load before the first spoke goes
  slack, traced over 720 directions. Drag the dot (mouse anywhere, finger on
  the dot) or use the sliders.

Both sections collapse with their title bar and remember that choice in the
browser, and both show the buckling note instead of a chart past buckling.

The URL hash carries the build, in the format defined by
`wheel-physics-core/js/build-link.js` (shared with
`wheel-comparison-widget2`): `#compare&h1=h6&h2=h7&w1=29&td1=120&ns=32`,
where `h1` is the 148x12 hub, `h2` the 157x12 hub, `w1` the rim size, `td1`
the drive-side tension in kgf and `ns` the spoke count. `App.jsx` reads it
once at load (missing or invalid values fall back to the defaults) and keeps
the hash in step with the settings afterwards, so the address bar is always a
link to the build on screen. The COMPARE tab's "Quick compare" link hands the
same build to the widget; the widget's "Explore why in the Lab" link does the
reverse. The smoke test covers loading a build link, the Quick compare
address, and a mangled link.

Beside the header's "Share link" button, "Copy result" copies the build on
screen as plain text for places that show no link preview, such as a
Pinkbike comment: lateral strength and lateral stiffness on separate,
labelled lines, the build (with the rim offset when it is not zero), a
credit to Ford's Mode Matrix method, and the link. The wording is
`wheel-physics-core/js/share-text.js`, which the widget's "Copy result"
uses too, so a pasted result reads the same from either tool.

## Deploying

`dist/index.html` is the same kind of file as the original — copy/upload it
to the `MTB-wheel-lab` repo's `index.html` via GitHub's web UI, exactly like
before. GitHub Pages picks it up automatically.

## Updating dependencies

React, ReactDOM, and Recharts are now real npm dependencies pinned in
`package.json` (currently the latest patch releases on the same major
versions the site already used — React 18, Recharts 2 — deliberately *not*
jumped to React 19 / Recharts 3, since those are breaking major-version
changes that would need real browser testing to validate safely, not just
a rebuild). To update:

```
npm outdated          # see what's behind
npm update             # bump within the ranges in package.json
npm audit               # check for known vulnerabilities
npm run test:all       # rebuild and re-run everything before deploying
```

For a major-version jump (e.g. Recharts 2 → 3, which changed internal
APIs), budget time for actual visual testing in a browser — the automated
tests here catch crashes and math regressions, not "does this chart still
look right."

`wheel-physics-core` is pinned differently from the other three — not to a
version number, but to an exact commit
(`github:postmillennium-MTB/wheel-physics-core#<sha>` in `package.json`),
so a build today and a build next year pull the exact same math unless
someone deliberately updates that pin. To pick up a change made in
wheel-physics-core, update that commit SHA by hand — `npm update` alone
won't move it — then re-run `npm run test:all` the same as for any other
dependency bump.
