# Wheel Strength Lab — source

This is the buildable source behind `postmillennium-mtb/MTB-wheel-lab`'s
`index.html`. The deployed site is still a single self-contained HTML file —
that hasn't changed — but it's now *generated* from real, readable source
files instead of being the only copy of the app that exists anywhere.

## Why this exists

The original `index.html` was a 600KB single-line minified bundle with no
separate source, frozen dependency versions, and no error handling if a
calculation crashed. This directory fixes that:

- **`src/`** — readable, organized source (see below)
- **`build.js`** — rebuilds `dist/index.html` from `src/` using esbuild
- **`test/`** — automated regression tests (physics math + a full-app smoke test)
- **`.github/workflows/test.yml`** — runs the tests on every push. This one
  lives loose in the repository rather than inside `wheel-lab-source.zip`,
  because GitHub only reads workflow files at that path in the repo itself and
  never looks inside an archive. See **Continuous integration** below.

## Continuous integration

Every push and pull request runs `.github/workflows/test.yml`, which unpacks
`wheel-lab-source.zip`, installs dependencies, rebuilds the bundle, runs both
test suites, and then checks that the committed `index.html` is byte-for-byte
identical to that fresh build. Green means the source is sound *and* the
deployed file is the one that source produces.

That last check is the point. Because `index.html` is uploaded by hand rather
than generated by the workflow, the failure this repo is actually exposed to is
the two drifting apart — the archive updated without re-uploading the built
file, or the deployed file edited without updating the archive. A build passing
proves the source works; only the comparison proves the source is what is live.
If it fails, download the `index.html` artifact attached to that run and commit
it.

The workflow needs the unpack step because the buildable source ships as a zip
rather than as loose files; `npm` cannot see `package.json`, `build.js` or
`src/` until it is extracted. The dependency audit runs but does not fail the
build: a new advisory published against a dependency would otherwise turn runs
red with nothing in the repo having changed, which only teaches people to
ignore red. Audit findings still appear in the run log.

## Where the physics comes from

The wheel-strength math itself doesn't live in this repo. It lives in a
separate, shared repo —
**[wheel-physics-core](https://github.com/postmillennium-MTB/wheel-physics-core)**
— because this tool and its sibling, `wheel-comparison-widget2`, used to
each carry their own hand-copied version of the same math, and those two
copies had quietly drifted apart. wheel-physics-core exists so that can't
happen again:

- It holds Matthew Ford's original reference math, **written in Python**
  (his `bike-wheel-calc` library, copied over unmodified — see that repo's
  README for the full attribution).
- It also publishes a **JS** (JavaScript — the programming language that
  runs inside a web page, in the visitor's own browser, with no server
  involved) port of that same math, hand-written to match the Python.
- Every time that JS changes, an automated check called **CI**
  (Continuous Integration — a script that runs by itself the moment code
  is pushed, rather than only when a person remembers to run it) recomputes
  the same numbers both ways — once in the real Python, once in the JS —
  and fails loudly if they don't agree. That check is what "validated"
  means here: not eyeballed once, but re-proven on every single change.

This repo (and `wheel-comparison-widget2`) are each **plain HTML** — no
server, nothing running behind the scenes. What they actually ship is the
JS half: `physics.js` imports the already-checked JS engine straight from
wheel-physics-core at build time (see `package.json`), so the Python never
runs live and never needs to — by the time its JS port reaches a visitor's
browser, wheel-physics-core's CI has already confirmed it matches the
Python, line for line. `wheel-comparison-widget2` has no build step, so it
keeps its own synced copy of that same engine file instead — the two tools
end up running byte-identical math either way.

Lateral strength (`F_lat`, the sideways load at which the first spoke goes
slack) and buckling tension come from Ford's fully-discrete-spoke Mode
Matrix, where each spoke sits at its own position around the rim and
lateral and radial deflection are coupled. Stiffness (`K_lat`, `K_rad`)
uses his smeared-spoke formulas. Until October 2026 strength also used a
smeared shortcut; wheel-physics-core's `validation/strength/README.md`
records why it was replaced. A build at or past its buckling tension has no
meaningful strength figure, and the COMPARE tab says so instead of showing
one (it happens on 32" rims at high tension).

Across the 30 hubs in the catalogue (`src/data.js`) at standard build conditions (29 in, 32H, 2.0 mm spokes, 100 kgf DS tension), K_lat ranges from **53.6 to 82.6 N/mm for 148** builds and **63.7 to 102.5 N/mm for 157** builds. The variation within each standard is as large as the difference between standards — meaning hub geometry and wheel size matter as much as the axle width.

### Does the ratio change with wheel size (27.5" vs 29")?

Yes, but only very slightly — wheel size is a minor, second-order effect on this particular metric. Running the actual engine across all four wheel sizes on a few different hubs:

| Hub | 26" | 27.5" | 29" | 32" | spread |
|---|---|---|---|---|---|
| CK Centerlock 157x12 | 71.85% | 71.82% | 71.77% | 71.72% | 0.14 pp |
| Project 321 G3 157x12 | 83.24% | 83.22% | 83.18% | 83.14% | 0.10 pp |
| DMR Zone Centerlock 148x12 | 55.64% | 55.61% | 55.57% | 55.51% | 0.14 pp |

(32H, 2.0 mm spokes, 100 kgf DS, re-run 2026-11-07 on wheel-physics-core
`1a8109f`. Project 321 G3 157x12 reads higher than the 81.6% this table
showed before the October 2026 correction to that hub's offsets.)

So going from 27.5" to 29" moves the ratio by roughly 0.05 percentage points — essentially nothing next to the tens-of-points spread you see just from switching hubs. The mechanism is real (larger wheel radius → both spoke bracing angles shrink slightly, and they don't shrink at exactly the same rate when the two flanges differ in offset or PCD, so the ratio drifts a hair), but it's swamped by hub geometry.

Worth noting: wheel size matters much more for the other three metrics — K_lat, F_lat, buckling tension — because those depend on absolute spoke length and rim stiffness, not just the angle ratio. The line above about "hub geometry and wheel size matter as much as axle width" is about K_lat, a stiffness, not tension balance.

## Tabs

| Tab | What it shows |
|---|---|
| COMPARE | The two chosen hubs side by side: tension balance, lateral stiffness (K_lat), lateral and radial strength (F_lat, F_rad, first spoke slack), buckling tension, the failure map and the spoke ring (both below), and a Quick compare link to the widget. |
| SYMMETRY | Interactive demo of how flange offsets set drive/non-drive tension balance, with a self-playing callout tour. |
| SIMULATION | A ride-load trace against each build's lateral strength, a slow-motion single impact, a deflection curve and an S-N fatigue curve. Stiffness and strength come from the engine; the ride loads, the past-first-slack part of the curves and the fatigue trend are illustrative, and the tab says so. |
| DEEP DIVE | The load envelope (below) and further detail charts for the two builds. |
| TENSION BALANCE | NDS/DS tension balance for every hub in the catalogue, with the rim-offset slider applied. |
| HUB SPECS | Sortable spec sheet of all 30 hubs: the measured flange offsets and diameters, plus flange spacing, bracing angles and tension balance derived from them. |
| TORSION | Pedal and brake torque. A torque spoke ring (strength: each spoke's tension under a torque, up to first slack) and wind-up stiffness (stiffness: torque per degree of rim rotation, collapsed by default). |
| INSIGHTS | Four further results, each with its study cited in MLA style and an EQUATION button: spokes sharing a hit (Ford, after Hetényi, Smith, and Pippard & Francis), tension softening of lateral stiffness (Ford), per-shape buckling tension (Ford, Papadopoulos & Balogun 2016), and spoke pitch with a playable keyboard (Allen, *Bike Tech*, 1984). |

Each lateral-strength chart carries a short ISO 4210-7 note (`IsoNote.jsx`):
the standard's static test checks a rim for permanent bending under a
sideways load, while F_lat is the earlier, elastic first-slack limit, so the
two are different thresholds.

## A note on code style in physics.js and App.jsx

`physics.js`'s remaining local math (`bracingAngleDeg`, `applyRimOffset`,
`tightSideFirst`, and the ride-simulation/fatigue helpers) and the bulk of
`App.jsx` are left in a dense, short-variable-name style on purpose, rather
than fully rewritten with descriptive names throughout. (The actual
strength/stiffness calculation, `computeWheelStrength`, isn't local code to
style at all anymore — it's imported from wheel-physics-core; see "Where
the physics comes from" above.) Two reasons:

1. **Risk.** Hand-renaming variables inside a 20-term trigonometric
   expression is exactly the kind of edit that can silently introduce a
   sign error nobody catches in review. Every rename that *was* made
   (function names, module-level data references, component names) was
   verified mechanically — reversing the rename and diffing against the
   original bundle byte-for-byte — rather than trusted by eye.
2. **What actually helps.** The value of "readable source" here is mostly
   about being able to *find* things (a named `physics.js` instead of one
   line of 600KB) and understand what a function *does* (via the comment
   above it), not about every local loop variable having a long name.

If you want to make the internals more readable too, that's a reasonable
follow-up — just do it function-by-function with the same verify-by-diff
discipline, not as one big pass.

## Building

```
npm install
npm run build       # writes dist/index.html
npm test            # physics regression tests (fast, no build needed)

```

## Failure map

The COMPARE tab ends with a FAILURE MAP (`src/components/FailureMap.jsx`):
load against drive-side spoke tension for the two selected hubs, straight
down or sideways. The solid line is the engine's first-slack load (`F_rad` /
`F_lat`, Ford's discrete-spoke Mode Matrix). The dashed line is `F_taco`,
Ford & Balogun (2017) Eq. 2, a rough rim-buckling estimate that applies to
straight-down loads only; it comes from `wheel-physics-core` along with
`K_lat0` and `R_rim`. The sweeps (40 kgf to each hub's buckling tension, 3 kgf
steps, about 100 engine calls) run after the tab paints, and use the selected
rim size, spoke count and rim offset. The stat under the chart is the area of
one hub's shaded zone against the other's, from 40 kgf to each hub's buckling
tension.

The map shares its HUB toggle and Play crossfade with the spoke ring below
it (`FailureViews.jsx` holds the state, `HubFade.jsx` the hook and
controls), so either section's controls move both.

## Spoke ring and load envelope

Both draw from `wheel-physics-core`'s per-spoke output
(`calc(..., { spokes: true })`, `spokeTensions`, `firstSlackCombined`): each
spoke's tension change per unit point load from Ford's discrete-spoke Mode
Matrix, checked against his bike-wheel-calc in that repo's
`validation/spokes/`. `spokeModel()` in `physics.js` runs it for one build and
maps the engine's tighter/looser sides back to the real drive side when
`tightSideFirst()` has swapped them.

- **SPOKE RING** (COMPARE, `SpokeRing.jsx`): every spoke's tension under one
  hit at the tire, straight down or sideways either way, with a strip chart
  of the same tensions by distance from the hit. One load in kgf applies to
  both hubs, so Play shows one going slack before the other. Exact in Ford's
  model up to first slack; the slider runs to 130% of it, and past first
  slack the readout says the picture is an extrapolation.
- **LOAD ENVELOPE** (DEEP DIVE, `LoadEnvelope.jsx`, its own hub picker): every
  combination of straight-down and sideways load before the first spoke goes
  slack, traced over 720 directions. Drag the dot (mouse anywhere, finger on
  the dot) or use the sliders.

Both sections collapse with their title bar and remember that choice in the
browser, and both show the buckling note instead of a chart past buckling.

## Links between the Lab and the 148 vs 157 widget

The URL hash carries the build, in the format defined by
`wheel-physics-core/js/build-link.js` (shared with
`wheel-comparison-widget2`): `#compare&h1=h6&h2=h7&w1=29&td1=120&ns=32`,
where `h1` is the 148x12 hub, `h2` the 157x12 hub, `w1` the rim size, `td1`
the drive-side tension in kgf and `ns` the spoke count. `App.jsx` reads it
once at load (missing or invalid values fall back to the defaults) and keeps
the hash in step with the settings afterwards, so the address bar is always a
link to the build on screen. The COMPARE tab's "Quick compare" link hands the
same build to the widget; the widget's "Explore why in the Lab" link does the
reverse. The smoke test covers loading a build link, the Quick compare
address, and a mangled link.

## Deploying

`dist/index.html` is the same kind of file as the original — copy/upload it
to the `MTB-wheel-lab` repo's `index.html` via GitHub's web UI, exactly like
before. GitHub Pages picks it up automatically.

## Updating dependencies

React, ReactDOM, and Recharts are now real npm dependencies pinned in
`package.json` (currently the latest patch releases on the same major
versions the site already used — React 18, Recharts 2 — deliberately *not*
jumped to React 19 / Recharts 3, since those are breaking major-version
changes that would need real browser testing to validate safely, not just
a rebuild). To update:

```
npm outdated          # see what's behind
npm update             # bump within the ranges in package.json
npm audit               # check for known vulnerabilities
npm run test:all       # rebuild and re-run everything before deploying
```

For a major-version jump (e.g. Recharts 2 → 3, which changed internal
APIs), budget time for actual visual testing in a browser — the automated
tests here catch crashes and math regressions, not "does this chart still
look right."

`wheel-physics-core` is pinned differently from the other three — not to a
version number, but to an exact commit
(`github:postmillennium-MTB/wheel-physics-core#<sha>` in `package.json`),
so a build today and a build next year pull the exact same math unless
someone deliberately updates that pin. To pick up a change made in
wheel-physics-core, update that commit SHA by hand — `npm update` alone
won't move it — then re-run `npm run test:all` the same as for any other
dependency bump.
